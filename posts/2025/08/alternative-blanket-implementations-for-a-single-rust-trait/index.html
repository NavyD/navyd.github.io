单个 Rust Trait 的替代总体实现

2025年8月10日17:57
阅读时长: 3 分钟
English

翻译于 Alternative Blanket Implementations for a Single Rust Trait

Rust 的特征系统非常强大，并且非常严格地避免歧义。

其中一条规则是，您不能 对可能 适用于同一类型的同一特征有多个总体实现。

什么是通用实现（Blanket Implementations）？

通用实现 (Blanket implementation) 是一种适用于 任何 满足特定约束的类型的特征实现，通常通过泛型实现。

标准库中的一个典型示例是如何 From 协同 Into 工作：

1
2
3
4
5

8

impl<T, U> Into<U> for T
where
    U: From<T>,
{
    fn into(self) -> U {
        U::from(self)
    }
}

得益于此，当你为 U 实现 From<T> ，T 会自动获得 Into<U> 。非常符合人体工程学！

限制

然而，Rust 强制执行一条关键规则：任何两个总体实现都不能重叠 ——即使 在理论上 也是如此。考虑一下：

1
2

impl<T: TraitA> MyTrait for T { ... }
impl<T: TraitB> MyTrait for T { ... }

即使当前没有类型同时实现 TraitA 和 TraitB，编译器也会拒绝此操作。原因何在？因为将来某些类型 可能会同时满足这两个条件，这将导致实现变得模棱两可。

现实世界的问题

在使用 Joydb 时，我遇到了这个确切的问题。

我有一个 Adapter 负责保存数据的特征。

在实际应用中，有两种常见的实现方式：

  • unified adapter 将所有数据存储在单个文件（例如 JSON）中。在 Joydb 中，这就是 UnifiedAdapter 。
  • partitioned adapter 将每个关系存储在单独的文件中（例如，每个关系一个 CSV），称为 PartitionedAdapter 。

理想情况下，用户只需要实现其中之一并 Adapter “免费”获得该特征。

但是 Rust 不允许我定义两个互相冲突的统一实现。所以……有什么解决办法吗？🤔

pub trait PartitionedAdapter {
    fn write_relation<M: Model>(&self, relation: &Relation<M>) -> Result<(), JoydbError>;

    fn load_relation<M: Model>(&self) -> Result<Relation<M>, JoydbError>;
}

所以问题就变成了：我怎样才能让某人实现 UnifiedAdapter 或 PartitionedAdapter ，然后 Adapter 自动获得？

解决方法：Associated Type + Marker Structs

我在 这个 Rust 论坛帖子 中发现了一个解决方案，我相信它值得更多人关注。

关键思想是使用：

  1. Marker structs 类似于 Unified<T> 并 Partitioned<T> 包装适配器类型。
  2. BlanketAdapter 为每种标记类型实现一个辅助特征。
  3. 特征中的 associated type 用于 Adapter 委托行为。

步骤 1：Marker Structs

1
2
3
4

use std::marker::PhantomData;

pub struct Unified<A: UnifiedAdapter>(PhantomData<A>);
pub struct Partitioned<A: PartitionedAdapter>(PhantomData<A>);

这些零大小类型仅用于类型级调度。

第二步：BlanketAdapter Trait

trait BlanketAdapter {
    type AdapterType;
    fn write_state<S: State>(adapter: &Self::AdapterType, state: &S) -> Result<(), JoydbError>;
    fn load_state<S: State>(adapter: &Self::AdapterType) -> Result<S, JoydbError>;
}

impl<A: UnifiedAdapter> BlanketAdapter for Unified<A> {
    type AdapterType = A;

    fn write_state<S: State>(adapter: &A, state: &S) -> Result<(), JoydbError> {
        adapter.write_state(state)
    }

    fn load_state<S: State>(adapter: &A) -> Result<S, JoydbError> {
        adapter.load_state()
    }
}

impl<A: PartitionedAdapter> BlanketAdapter for Partitioned<A> {
    type AdapterType = A;

    fn write_state<S: State>(adapter: &A, state: &S) -> Result<(), JoydbError> {
        S::write_with_partitioned_adapter(state, adapter)
    }

    fn load_state<S: State>(adapter: &A) -> Result<S, JoydbError> {
        adapter.load_state()
    }
}

现在我们有了 不冲突的通用实现，因为它们适用于 不同的类型 （ Unified<A> vs. Partitioned<A> ）

步骤 3：Adapter关联类型的特征

pub trait Adapter: Send + 'static {
    type Target: BlanketAdapter<AdapterType = Self>;

    fn write_state<S: State>(&self, state: &S) -> Result<(), JoydbError> {
        <Self::Target as BlanketAdapter>::write_state(self, state)
    }

    fn load_state<S: State>(&self) -> Result<S, JoydbError> {
        <Self::Target as BlanketAdapter>::load_state(self)
    }
}

关键部分：关联类型 Target 告诉 Adapter 是否委托给 Unified<Self> 或 Partitioned<Self> 。

pub struct JsonAdapter { ... }

impl UnifiedAdapter for JsonAdapter {
    fn write_state<S: State>(&self, state: &S) -> Result<(), JoydbError> {
        // write entire state to JSON
    }

    fn load_state<S: State>(&self) -> Result<S, JoydbError> {
        // load state from JSON
    }
}

impl Adapter for JsonAdapter {
    type Target = Unified<Self>;
}

没有代码重复，没有冲突。唯一的开销是额外增加 3 行代码来连接代码

最后的想法

这种模式 - 使用 marker types + associated types - 使你能够在遵守 Rust 的一致性规则的同时，灵活地 实现替代的通用实现。

它特别适用于在统一的接口下支持相互排斥的行为，同时不牺牲人体工程学设计。
